# Change add-pi-adapter

## Pourquoi

session-dig n'archive aujourd'hui qu'une seule source : `opencode.db`. L'environnement réel en compte deux : les sessions **pi** vivent en JSONL append-only sous `~/.pi/agent/sessions/<cwd-encodé>/*.jsonl` (63 fichiers observés), avec des décisions, des échecs et des preuves qu'aucune requête `sdig` ne peut atteindre. La spec corpus a prévu ce cas dès la v0 (« tout futur adaptateur SHALL produire exactement le même schéma », le cœur ne lit jamais une source) — mais deux points bloquent en pratique : aucun adaptateur pi n'existe, et `state.json` ne porte qu'**un** watermark (`{message, session}` en epoch ms sur `time_updated` d'opencode), inapplicable à une source de fichiers append-only sans horloge globale.

L'objectif est un **corpus fusionné** : une seule recherche couvre les sessions des deux agents. Le format pi mappe bien sur le schéma canonique (usage → tokens/cost, parts text/toolCall, `exitCode` exposé par les rôles `bashExecution` — que la source opencode n'offrait pas) ; la vraie difficulté est l'état incrémental multi-source, pas le mapping.

## Quoi change

- **ADDED** — adaptateur **pi** : lecture stricte en lecture seule du répertoire de sessions JSONL, mapping vers le schéma canonique v1 (événements user/assistant, `toolCalls` avec `exitCode` et `rawRef` raccrochés depuis les messages de résultat `toolResult`/`bashExecution`), sessions avec `directory`/`repo`/titre dérivé, `tokens`/`cost` agrégés depuis `usage`.
- **MODIFIED** — ingestion incrémentale : `state.json` devient **multi-source** (`sources.opencode` : watermark `time_updated` inchangé ; `sources.pi` : état par fichier `{size, mtimeMs}`, relecture complète d'un fichier changé — jamais de reprise à l'octet ; un changement de chemin d'une source invalide son état seul). L'ancienne forme plate est migrée au premier passage. Le protocole de publication (marqueur → staging → COMMIT de la vue → state.json) couvre le delta de toutes les sources en une seule passe ; la fraîcheur de la vue devient par source (jeton déterministe) ; l'égalité de rebuild est qualifiée « depuis les mêmes sources » (l'archive conserve des sessions dont la source a disparu sans être reconstructible — ce n'est pas une divergence).
- **MODIFIED** — schéma canonique v1 (additif, sans bump) : toute ligne session/événement **produite après ce change** porte un champ `source` (`"opencode"` ou `"pi"`) ; les lignes opencode héritées ne sont pas réécrites pour seule addition du champ (lues comme opencode). Les identifiants pi de session/événement sont préfixés `pi:`, et les `partId` de preuve **qualifiés par session** (`pi:<sessionId>:<id local>`) pour garantir l'absence de collision de shards et de preuves entre sources et entre sessions. Les identifiants opencode existants ne changent pas — le corpus en place n'est pas réécrit.
- **ADDED** — registre de sources : défaut = `opencode.db` + `~/.pi/agent/sessions` ; `--db`/`SESSION_DIG_DB` deviennent propres à la source opencode, `--pi-dir`/`SESSION_DIG_PI_DIR` à la source pi ; `--source all|opencode|pi` sélectionne. Source par défaut absente = signalée explicitement, sans erreur ; source demandée explicitement absente = erreur.
- **MODIFIED** — CLI de recherche : filtre `--source S` (borne aussi le scan `--raw`), provenance des lignes de titre.
- Les branches pi (chaîne `parentId`) sont **aplaties** par (`ts`, `id`) en v0 — perte documentée, pas silencieuse. Lignes `compaction`, `branch_summary`, `custom`, `model_change` et rôles `system` : ignorées en v0, réversibles par rebuild.
- Fichiers pi en cours d'écriture (session vivante) : ingestables — dernière ligne partielle ignorée, reprise à la passe suivante.

## Impact

- **Specs** : deltas `corpus` (schéma, ingestion, adaptateur pi, registre) et `search` (filtre CLI `--source`).
- **Code** : `src/adapter/pi.js` (+ extraction partagée si utile), `paths.js` (source pi), `corpus.js` (état multi-source, boucle multi-adaptateurs — le contrat `adaptPaged`/batch par session est conservé), `bin/sdig.js` (options), `format.js`/`view.js` (affichage du watermark par source, colonne/`--source`).
- **Corpus existant** : inchangé octet par octet pour les lignes et shards opencode lors de la première ingestion pi — vérifié par comparaison des **empreintes par fichier** (`sdig fingerprint` liste les md5 individuels ; l'empreinte globale change par construction : nouveaux shards pi, `state.json`, vue). L'ajout additif `source` aux lignes opencode modifiées aux ingestions suivantes est accepté et documenté : la stabilité s'apprécie pour un même ensemble de sources et les mêmes règles de sérialisation. Constat du 16/09 conservé : une modification remplace la ligne — pour pi, « modification » = le fichier a changé.
- **Confidentialité** inchangée : corpus local uniquement, jamais publié ; les sessions pi peuvent contenir du matériel sensible (jetons, chemins Termux) — même règle que opencode, fixtures synthétiques seulement pour les tests. Même avertissement que le change MCP : ce que le CLI (ou le futur serveur MCP) retourne peut être transmis au fournisseur du modèle appelant.
- **Hors périmètre** : serveur MCP (change `add-mcp-server` déjà spécifié), embeddings/RRF, `sstats`, sous-agents pi comme champ `agent`, restitution des branches pi, ingestion du jeu d'évaluation.
