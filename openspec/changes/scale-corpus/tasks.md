Réussite : aucun chevauchement des sections protégées, aucun processus ne retire le verrou d'un autre, le concurrent échoue explicitement sans mutation ; un verrou ambigu est refusé conservativement, sans promesse de reprise automatique. *(SOLDÉ le 01/10/2026 — verrou noyau SQLite via `better-sqlite3`, déjà dépendance du projet, **aucune installation**. `src/lock.js` distingue **création neuve** (réservation exclusive `O_CREAT|O_EXCL`, seul le créateur initialise) et **artefact déjà présent** (validation LECTURE SEULE du schéma, aucune écriture de structure) : `locking_mode=EXCLUSIVE` + `BEGIN EXCLUSIVE … COMMIT` conserve le verrou exclusif noyau (second processus ⇒ `SQLITE_BUSY`) ; le fichier de verrou n'est jamais supprimé. Un artefact **vide, illisible, symlink (cible intacte) ou base SQLite étrangère** est REFUSÉ sans remplissage. Une trace propriétaire commitée subsistant verrou noyau libre ⇒ refus conservateur (pas de reprise automatique). 13 tests ciblés dont des scénarios multiprocessus IPC (`test/lock-concurrency.test.js`) : artefacts ambigus refusés/intacts, schéma exact sans objet étranger ; course de première initialisation et barrière après réservation avant initialisation (un seul crée/initialise, concurrent refusé sans remplir le fichier vide) ; propriétaire vivant (BUSY) et mort (trace, reprise opérateur) ; deux repreneurs refusés ; contention à 3 ; acquire idempotent + seconde instance même process refusée (fermeture perdante sans effet, vérifiée par un tiers) ; échecs init/COMMIT (aucune connexion conservée, état conservateur) ; entrelacements de libération avant release et **après le COMMIT du DELETE avant close** (concurrent refusé malgré trace effacée) ; ingestion concurrente refusée. Limites honnêtes : protection coopérative vis-à-vis du fichier — le protocole ne le supprime jamais, mais un acteur qui le supprime hors protocole casse l'exclusion (nouvel inode) ; pas de durabilité matérielle ; `locking_mode=EXCLUSIVE` bloque aussi les lectures concurrentes. **Frontières d'arrêt brutal** : seule une **trace commitée** ou un **init ambigu** refuse ; un crash pendant `release` après le COMMIT du DELETE et avant la fermeture laisse un état **libre légitime**. Détail : progress.md « Validation A1 PRoot du 01/10/2026 ».)*
